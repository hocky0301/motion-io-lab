# 設計判断とその理由

この文書は「なぜそうしたか」だけを書く。何が動いていて何が未検証かは `STATUS.md`、言えることと言えないことの対応は `CLAIMS.md`。

用語: **ラッチ**＝止まった状態を保ち、人が `CLEAR` するまで戻らないこと。**スルー**＝1 秒あたりに動かしてよいパルス幅の上限。**デッドマン／期限（lease）**＝送り続けないと止まる仕組み。**epoch**＝接続ごとにデバイスが出す世代番号。**適用値**＝ファームが PWM チップへ書いた値（位置ではない）。

## 0. 問いと、問いに合わせた形

問い: 人の入力を記録して再生したとき、実物はどこまで同じ動きをし、違いはどこで生まれるか。

「違いがどこで生まれるか」に答えるには、動きが通る段を分けて記録する必要がある。そこで 1 回の試行を 3 本のログに分けた。

```
人の入力 ──(整形)──> 指令 ──(受信側の期限・スルー制限)──> 適用値 ──(サーボ・機構)──> 実際の動き ──(カメラ)──> 観測
 input.jsonl          command.jsonl (set)                  command.jsonl (reply)                                 observation.jsonl
```

- 指令（`commanded_*`）、ファームの適用値（`device_applied_*`）、カメラの観測（`observed_*`）は**別の列・別の系列**。1 つにまとめない。
- 再生と録音の差を、指令・適用値・観測の 3 段で別々に出す（`fig3_error_ladder.png`）。**段の大小がそのまま「差の生まれた場所」を指すとは限らない。** 指令の段は解析の格子と送信時刻のゆらぎで決まり、観測の段は検出器の雑音の床と、録音の開始状態に左右される（5 の実験）。段ごとの数字は、注入した雑音源を 1 つずつ切って確かめたうえで読む。
- 「指令した角度」を「実測した角度」と呼ばない。適用値（PWM チップへ書いた値）も位置ではない。

## 1. 試行ログ v1（`triallog.py`, `docs/trial_schema_v1.json`）

| 判断 | 理由 |
|---|---|
| 入力・指令・観測を別ファイル（`input.jsonl` / `command.jsonl` / `observation.jsonl`） | 観測はカメラを回す別プロセスが書く。1 ファイルに混ぜると書き込みが競合し、「どの列が何の時計か」が曖昧になる |
| 1 行目は必ず header。以降の全行に共通フィールド（`docs/trial_schema_v1.json` の `common_fields`）を持たせる | 行を 1 本切り出しても単位・時計・出どころが読める。検証器が行番号つきで欠落を指せる |
| `<name>.jsonl.part` に書いて閉じたときに公開（`os.link` で既存を上書きしない） | 途中で落ちたログが正規の名前で残らない。追記も上書きも構造上できない |
| `capture_time_ns` は既定で null、`capture_time_provenance=unknown` | OpenCV は露光時刻を出さない。受信時刻で埋めると「露光時刻」と読めてしまう。null と provenance の組み合わせが食い違う行は検証で落とす |
| `calibration_version` は `record` / `play` / `observe` に `--calibration <file>` を渡したときだけ入る（校正ファイルの版）。渡さなければ null | 校正は測ってから決まる物。ログを取る時点で無い校正を埋めない。デモでは校正を解析のときに当て、版は `summary.json` に入る |
| `valid=false` の行は値を null（0 で埋めない）、理由は `invalid_reason` | 欠測を 0 度として平均に混ぜる事故を防ぐ。理由（none_found / multiple_blobs / …）が後から失敗を説明する |
| 同じ `session_epoch` の中で `seq` が増加しなければ検証エラー | 再送・順序逆転がログに残っていないかを後から機械的に確認できる |
| `mode`（DRY_RUN / LOOPBACK / HARDWARE_ARMED / REPLAY）と `link`（none / virtual / serial）を別にした | REPLAY は「保存した指令を再発行した」という活動で、どこへ出したかは別。この分け方で、再生をドライ・仮想・実機のどれへ向けたかを区別できる |
| `source`: 仮想デバイスか台本入力なら `synthetic`、人の入力だけを保存したドライなら `recorded`、シリアルなら `hardware`。動画から作った観測は `rendered_video` | 合成を実測に見せない。ヘッダとログの全行に残る |

## 2. プロトコル v2 とファーム（`guarded_servo_core.h`）

この repo の公開前の版（非公開）で見つけた 3 つの反例が出発点。いまのコードは次を拒否し、試験で縛っている（`tests/test_vdevice.py`、`summary.json` の `failure_cases`）。`ARM`→`SET 1`→`DISARM`→`ARM`→`SET 1` と同じ列を再送すると、もう一度受理された。`SET` を二重送信すると fault が立った。`SET -1` が `4294967295` として読まれた。

| 判断 | 理由 |
|---|---|
| `HELLO` のたびにデバイスが新しい epoch を発行する。`ARM <epoch>` と全 `SET` が epoch を持つ | 再接続した別の接続で、前の接続の `ARM`/`SET` を再送しても世代が違うので受理されない。epoch は認証ではない（シリアルに繋げる人なら読める）。目的は「古い列が無害に拒否される」こと |
| どんな停止（DISARM / ESTOP / 期限切れ / HELLO）でも epoch を 0 にする | 再武装には新しい `HELLO` が要る。同じ接続内でも、DISARM 前の `ARM` を再送して再武装される経路が無い |
| 重複した `seq` は `ACCEPTED_NOT_EXECUTED SET seq=N dup=1` を返すだけ。値は取り込まず、期限も延ばさない | 再送は無害に扱う。期限を延ばすと、最後の `SET` を再送し続けるだけで武装を保てる |
| 古い `seq`、別 epoch、範囲外、期限外れの `SET` は `REJECTED reason=…`。fault は立てない。期限も延ばさない | 誤った入力 1 回で CLEAR→再初期化が要るのは運用上の負担。拒否が続くだけなら期限切れで止まるので、安全側は保たれる |
| 数値は 10 桁以内の符号なし 10 進だけ（`parseU32`）。`-1`、`+1`、`15e2`、`0x5DC`、`1500-` は `parse` で拒否 | `sscanf("%lu")` は負号を受け付けて巨大な数にする |
| `valid_for_ms`（20〜500）は**受信側の時計**で期限を測る。最後に受理した `SET` から数える。期限が切れたら止めて fault を立てる（デッドマン） | ホストとデバイスの時計は合わせられない。デバイスが自分の時計だけで判断できる形にした。ホストが消えた場合が最も危険なので、期限切れは「ラッチして人が CLEAR する」まま |
| `ARM` の猶予は 300 ms | `ARM` 後に最初の `SET` が来ない場合も止まる |
| 返事は `REJECTED` / `ACCEPTED_NOT_EXECUTED` / `EXECUTED`。`EXECUTED` は「そのシーケンスに対応する PWM 書込みをした」であって、位置を測ったのではない | 応答が早く返ること自体は動作の証拠ではない |
| `STATUS` は `commanded_us`（受理した目標）と `applied_us`（最後に書いた値）を別に出し、`last_reject` と `last_stop` の理由コードを持つ | 「何を頼んだか」「何を書いたか」「なぜ止まったか」を後から分ける |
| 再武装は直前の適用値から始める（中央へ戻さない） | ARM のたびに中央値へ飛ばす作りだと、サーボは最後の位置から動かずに残っているので、再武装直後の最初の SET で中央への急な移動が起きる |
| 出力は最初の有効な `SET` まで無効（OE は HIGH のまま） | 起動直後に出力が出ないようにする |
| PWM レジスタ書込みは変化したときだけ、ch0 の 4 バイトを 1 トランザクションで | データシート 7.3.3: 4 レジスタが揃った最後の ACK で出力が変わる。毎 10 ms 2 回書いていた分が減る |
| `ALL_LED_OFF_H = 0x00` の書込みを削除 | 下の §2.1 |
| 入力あふれ・制御文字は、その行を捨て、行末で `REJECTED LINE reason=bad_line` を 1 回返す。武装中なら `STOP bad_line` を 1 回だけ | 残りの断片をもう一度コマンドとして処理すると `STOP` が 2 回出る |
| `HARDWARE_VERIFIED = false` のまま公開。`ARM` は `REJECTED hardware_verified_false` | チェックリストを終えてから手で `true` にする。ホスト側の `--i-checked-hardware` は自己申告にすぎない |

### 2.1 PCA9685 の `ALL_LED_OFF_H`

公開前の版は、チャンネル 0 のパルスを書くたびに `ALL_LED_OFF_H` へ `0x00` を書いていた（「ALL の上書きを解除するだけで他は全 OFF のまま」というコメントつき）。

NXP の PCA9685 データシート Rev. 4（https://www.nxp.com/docs/en/data-sheet/PCA9685.pdf）で確認した事実:

- Table 8（7.3.4）: `ALL_LED_OFF_H` の bit 4 は「ALL_LED full OFF」（write only）、bit 3:0 は全 LED の OFF カウント上位 4 bit。レジスタ表（Table 4）の説明は「全 LEDn_OFF レジスタの byte 1 をロードする」。
- 7.3.4 の本文: ON と OFF のカウントレジスタに同じ値を入れてはならない。
- 7.3.3: 4 つのチャンネルレジスタを全部書いた最後の ACK で出力が変わる。

つまり `0xFD` へ `0x00` を書くと、**16 チャンネル全部**の full-OFF ビットが消え、ch1〜15 は ON=OFF=0（同値）という、データシート上は未規定の状態になる。チャンネル 0 だけを使う現状では実害が小さいが、2 軸目を ch1 に挿した瞬間に未規定の出力になる。しかも ch0 自身の `OFF_H` の書込み（bit 4 = 0）が ch0 の full-OFF を消すので、`0xFD` の書込みは不要だった。削除した。停止時の `0xFD ← 0x10`（全チャンネル full OFF）はデータシートの「orderly shutdown の最速の方法」（脚注）と一致するので残した。

実機やオシロで確かめたわけではない。公開前の版のコードがデータシートの記述と逆向きだったので、データシートに合わせて書き換えた、という範囲。

### 2.2 プロトコル核を共有する（`guarded_servo_core.h`）

状態機械を Arduino のヘッダに依存しない 1 つのヘッダにして、スケッチ（`.ino`）とホスト用ハーネス（`tests/firmware_host/harness.cpp`）の両方が同じファイルを include する。テストが叩くのは、ボードにコンパイルされるのと同じ論理。

Python の `VirtualDevice` はこの核の**モデル**で、別実装。2 つが分かれないように、`tests/test_conformance.py` が同じ台本（手書き 1 本と、場面ごとの台本 4 本と、ほぼ正しいトラフィックに破損を混ぜた乱数 60 本）を両方へ流して、返事の行と I2C/OE の書込み列を 1 行ずつ比べる。片方だけ直すと落ちる。

ただしこれは ESP32 上の実行ではない。ホストの CPU、スタブの HAL（I2C は常に ACK、時計は台本が進める）での実行。`float` は ESP32 の `lroundf` と同じ式だが、実機での丸めまで確かめてはいない。

## 3. ホスト側

### 3.1 整形と再生

- 入力 [-1, 1] → 中央 ± `span_us`（既定 40、デバイスは ±50）→ ホストの範囲クランプ → ホストのスルー制限（既定 400 us/s、デバイスは 500 us/s）。ホスト制限をデバイスより低くして、通常はデバイス側の制限に当たらないようにした。`desired_pulse_us`（整形前）と `commanded_pulse_us`（整形後）を両方残すので、整形がどれだけ効いたか（`shaping`: clamp / slew）が後から分かる。
- ホストの範囲はデバイスの範囲の内側に限る（`Shaper` が外側を拒否）。
- 再生は**ホストの単調時計の締切**（開始 + i × 周期）で送る。「送った後に 1 周期 sleep」は遅れが積算する。**仮定した起床遅れのモデル**（指数分布、平均 0.12 ms）の下での計算で、締切方式のドリフトは数 ppm 以下（8 seed で −2.4〜+1.3 ppm、符号に意味は無い）、sleep 後方式は 6900〜7700 ppm（合成。`fig5_pacing.png`、`reference_results/seed_table.json`）。実機の `time.sleep` の遅れは別に測る。遅れは常に「理想の締切」に対して記録する。
- 締切から 60 ms を超えて遅れた指令は送らず（ちょうど 60 ms は送る）、`drop_reason=late` で記録する（古い指令を後から送らない）。
- 再生は録音より速くしない（`speed ≤ 1`）。上げるなら `max_speed` を意図して設定する。区間（`--start-ms/--end-ms`）の再生は可能。
- 中断（ケーブル抜け、デバイスの STOP、「もう接続ではない」系の拒否）で再生は止まる。**自動では再開しない**。再開は `--resume continue|restart` を付けたときだけで、順序は HELLO（新 epoch）→ ラッチしていれば CLEAR（`--allow-clear` が人の判断として要る）→ 実機ならもう一度タイプ確認 → ARM → デバイスが報告した適用値から整形し直して合流。
- 実機（`--target hardware`）は `--port`・`--i-checked-hardware`・端末での文字入力（`ARM <port>`）の 3 つが要る。ファーム側にも `HARDWARE_VERIFIED` の鍵がある。

### 3.2 入力

- キーボード: 端末を cbreak モードにして、終了時に必ず戻す。
- スマホブラウザのタッチパッド: 標準ライブラリの HTTP。既定は 127.0.0.1。`--lan` で全インターフェースへ開くが、**トークンはどちらでも必須**（毎回ランダム、定数時間比較）。ボディ 64 KB、1 回 500 イベントまで。範囲外・非数は拒否（丸めない）。ブラウザの `performance.now()` はホスト受信時刻と**別の列**（`client_time_ms`）に残し、8 回の往復で時計差の推定（最小 RTT の標本）も `sync` レコードとして残す。
- Joy-Con: Swift のプローブが JSON 行を出し、`--source joycon:<要素名>` で標準入力から読む。実機で動かしてはいない（`docs/JOYCON.md`）。

### 3.3 観測

- 設定（HSV 範囲、面積、ピボット、基準角、角度スケール）は検証して、欠落は `ConfigError`（生の `KeyError` を外へ出さない）。設定のハッシュ（先頭 8 桁）を header に残す。
- マーカーが 0 個なら `none_found`、2 個以上なら `multiple_blobs`。「もっともらしい方」を選ばない。値は null。
- 動画ファイルの時間軸は `media_pos_ms`（フレーム番号 / fps）。受信時刻は「デコードした時刻」で、露光とは無関係（`received_time_meaning` に書く）。動画の 0 がコマンド時間軸のどこかは**仮定**で、`--media-offset-ms`（既定 0）で明示する。
- 描画した動画で通す自己テスト（動く点を描く → mp4 に符号化 → 読み戻し → 検出）で、カメラ無しに観測経路を検査する。マーカー位置のゆらぎが 0 の理想条件で、mp4 圧縮を通しても角度の RMS 誤差は 0.06〜0.08°（5 つの乱数）、最悪のフレームで 0.19°。位置が 0.3 px ゆらぐと 0.13〜0.15°、1 px で 0.37〜0.42°（半径 140 px で 1 px ≒ 0.41°）。`scripts/observe_selftest.py` が出す（`reference_results/observe_selftest.json`）。これは**合成画像上の検出の確認**であって、実カメラの精度ではない。OpenCV 4.9 の mp4 往復では誤差が大きく（RMS 0.037 正規化 > 0.03）、デモの数字も動くので、対応外にした（`requirements.txt`）。

### 3.4 解析

- 3 系列を 10 ms の共通格子へ。指令と適用値は 0 次ホールド、観測は線形（穴が 120 ms を超えたら NaN。端の外へ外挿しない）。
- 遅れの推定は正規化相互相関＋放物線補間。**総遅れ**（サーボ応答＋カメラ経路＋時間合わせの仮定）で、カメラ遅延そのものではない。
- 再現性の指標: 5 回の再生の時点ごとの標準偏差（ddof=1）の RMS。録音との差: 再生の系列と録音の系列の RMS 差。
- **指令の段**が 0.1° 前後出るのは、同じ値の列でも送信時刻が 1 ms ずれると階段の段差が格子 1 点分ずれるため。再生は録音と同じ値を同じ順番で送っており、サンプルごとに比べた差は 0（`rms_deg_commanded_replay_vs_recording_by_sample`）。格子を 2 ms にすると 0.05°、40 ms にすると 0.19°（3 動作 × 2 seed の平均）と、格子の幅で値が動く（`reference_results/ablation.json`）。この段は「送信時刻のずれの統計」（`send_lateness_ms_p95`）と合わせて読む。
- **観測の段**には、検出器の雑音の床がある。動かないマーカーを同じ経路（mp4 とマーカー検出）で読んだ角度の SD（`observation_noise_floor`、デモで 0.046°）の √2 倍（0.065°）が、独立な 2 回の読みの差の目安。観測の段がこの高さなら、サーボの差は見えていない。5 回の再生の SD も同じ床の上にある（`pooled_sd_minus_floor` に床を引いた値を出す。n=5 の SD には約 35 % の不確かさがある）。
- 録音を基準にしない指標として、再生どうしの差（各再生と、ほかの再生の平均との RMS。`rms_deg_replay_vs_replay_*`）と、最初の 0.5 秒を除いた差（`*_after_500ms`）を併記する。
- 観測の穴（無効フレーム）は、前後の有効フレームの間の直線で埋めた格子点として指標に入る（`observation_bridged_fraction` がその割合）。
- 総遅れの推定は、波形に依存して動く。指令→観測は 116〜130 ms（seed 7。8 seed では 116〜131 ms）、適用値→観測は 89〜113 ms（seed 7。8 seed では 85〜113 ms）。2 つは別の区間の量で、まとめて 1 つの幅にはしない。ノイズの無いサーボの角度に同じ推定器を当てて作った期待値（`*_expected` = その遅れ + カメラ遅れ 70 ms）と並べると、動画経由の推定との差は約 3 ms 以内（個々の再生の最大 3.2 ms）で、動作ごとの差は動画のせいではなく波形と推定器の性質（不感帯と一次遅れ）による。実物のカメラ遅れが分かるわけではない。

## 4. 合成デモで何を仮定したか

デモは仮想デバイス・合成サーボ・描画動画だけで全工程を通す。仮定は `summary.json` の `synthetic_assumptions` と `motion_io_lab/synth.py` に書いてある。結果を良く見せる向きの仮定を含めて全部書く。

- サーボ: 一次遅れ（τ = 50 ms）、不感帯（0.12° の ±50 %。0.1°/us で約 1 us）、速度上限 300°/s、ゲイン 0.1°/us、試行ごとに 1 % のゲイン変動。**測った値ではない。** 実物の安いサーボの不感帯はもっと大きいことが多い（これも測っていない。`ablation.json` に 0.5° ≒ 5 us の場合を入れた）。
- 開始状態: 各試行をホーンが角度 0 の状態から始める（「homed」）。前の試行の終わりの位置を持ち越すと、観測の段の最初の 0.5 秒が大きくなる（5 の実験）。
- カメラ: 遅れ 70 ms、30 fps、3 % の欠測（独立で、連続しない）、3 % の 2 個目の点、mp4 圧縮。フレームの位相は毎回同じ（フレーム k は最初の指令から k/30 秒）。実カメラではフレームの位相も毎回ずれる。
- マーカー: 理想の円。位置のゆらぎ 0 px、画像ノイズ σ = 3 階調。実物のマーカーは揺れるので、検出誤差は下限（`reference_results/observe_selftest.json`: ゆらぎ 1 px で 0.4°）。
- 解析の側の仮定: 角度の校正にプラントのゲインそのもの（0.1°/us）を使う（校正は構成上、誤差 0）。動画の 0 秒の位置は既知（最初の指令と同時）。
- リンク: 片道 0.4〜0.7 ms、ホストの起床遅れ（指数分布 平均 0.12 ms、1 % が最大 4 ms）。
- 人の入力: 台本の動き＋ガウスの手ぶれ（σ = 0.01）。

この結果は「道具と指標が動く」ことを示す。実物のサーボやカメラについては何も言わない。数字は 1 つの乱数列（seed 7）の 1 回で、seed を変えると動く（8 seed の範囲: `reference_results/seed_table.json`）。

## 5. 段の読み方を確かめる実験（`scripts/ablation.py`）

「録音と再生の差を 3 段で出せば、差の生まれた段が分かる」は、そのままでは言えない。確かめるために、仮定した雑音源を 1 つずつ切る／強めて、どの段の数字が動くかを見た（seed 3 と 7、動作 3 つ、各 5 回再生。`reference_results/ablation.json`、表は `docs/CLAIMS.md` の S-B01b）。

| 変えた物 | 指令 | 適用値 | 観測 | 観測（最初の 0.5 秒を除く） | 観測の再生どうし | 観測の SD |
|---|---|---|---|---|---|---|
| `baseline`: デモの仮定のまま（各試行をホーン角 0 から始める） | 0.093 | 0.045 | 0.069 | 0.069 | 0.056 | 0.050 |
| `carry_over_start`: 前の試行の終わりの位置から次の試行を始める | 0.093 | 0.045 | 0.129 | 0.068 | 0.056 | 0.051 |
| `gain_jitter_off`: 試行ごとのゲイン変動を切る（1 % → 0） | 0.093 | 0.045 | 0.067 | 0.067 | 0.052 | 0.047 |
| `gain_jitter_5pct`: 試行ごとのゲイン変動を 1 % ではなく 5 % にする | 0.093 | 0.045 | 0.143 | 0.158 | 0.092 | 0.084 |
| `deadband_off`: 不感帯を切る（0.12° → 0） | 0.093 | 0.045 | 0.081 | 0.086 | 0.059 | 0.054 |
| `deadband_0p5deg`: 不感帯を 0.12° ではなく 0.5°（約 5 us）にする | 0.093 | 0.045 | 0.074 | 0.076 | 0.057 | 0.051 |
| `timing_jitter_off`: ホストの起床のゆらぎと回線の遅れのゆらぎを切る | 0.000 | 0.039 | 0.066 | 0.068 | 0.054 | 0.049 |
| `camera_dropout_off`: マーカーの欠測と 2 個目の点を切る | 0.093 | 0.045 | 0.068 | 0.069 | 0.052 | 0.047 |
| `marker_noise_1px`: マーカー位置のゆらぎを 1 px にする（デモは 0） | 0.093 | 0.045 | 0.491 | 0.496 | 0.399 | 0.358 |

RMS（deg）、3 動作 × 2 seed の平均。左の列の名前は `reference_results/ablation.json` の `variant`。「観測の再生どうし」は録音を使わない差。読み取り:

- **送信時刻のゆらぎを切ると、指令の段が 0.093 → 0.000 になる**（適用値は 0.045 → 0.039 と少し動く）。指令の段の正体は、送信時刻のずれを格子で見た量。サーボやカメラの差ではない。
- **録音の開始状態を持ち越すと、観測の段は 0.069 → 0.129 に増えるが、最初の 0.5 秒を除くと 0.068 のまま**。持ち越す設定では観測の段が指令の段より大きく見えるが、主因は録音が最初の試行で、再生は前の試行の終わりの位置から始まること。デモの既定は各試行をホーン角 0 から始める設定。
- **ゲイン変動は、1 % では見えない**（切っても 0.067。床に埋もれる）。5 % にすると観測の段が 0.143、5 回の SD が 0.084 に増える。
- **不感帯**は 0 / 0.12° / 0.5° でほとんど動かない（0.081 / 0.069 / 0.074。差は床の揺れの範囲）。
- **欠測・2 個目の点を切っても**、段の値は動かない（0.068）。数えられるのは無効フレームの数だけ。
- **マーカー位置のゆらぎ 1 px** で観測の段は 0.491 になり、床の上げ下げがそのまま出る。
- 指令の段は解析の格子の幅でも動く: 格子 2 / 5 / 10 / 20 / 40 ms で 0.05 / 0.07 / 0.09 / 0.13 / 0.19°（3 動作 × 2 seed の平均。`command_stage_by_grid_ms`）。

つまり、3 段は「注入した雑音源が検出の床より十分大きいとき」に、その源に対応する段が動く道具として働く（送信時刻 → 指令の段、開始状態 → 観測の最初の 0.5 秒、ゲイン変動 5 % と位置のゆらぎ → 観測の段）。しかしデモの既定値では、観測の段（0.06〜0.08°）は床の高さ（0.065°）にあり、「差がどこで生まれたか」を言える状態ではない。実機でこの読み方を使うときは、まず動かさない試行で床を測る（`docs/HARDWARE_RUN.md`）。

## 6. 作らなかったもの

- 自動の再接続・再武装・ハートビート。ホストが消えたときにデバイスを生かし続ける仕組みは作らない（デッドマンが働くべき場面だから）。
- ATOMS3 Lite のピン割当（`docs/BOARDS.md`）。
- 2 軸。
- 角度（度）で指令する API。校正（パルス→角度）は自分で測って `calibrate` に入れるまで存在しない。

## 7. 関連（先行する仕組みとの関係）

出典は 2026-10-09 に開いて確認した。ここで書くのは各ページが述べている範囲だけ。

- **ROS 2 の rosbag2**（https://github.com/ros2/rosbag2）は、ROS 2 の通信を記録して再生する仕組み（`ros2 bag record` / `ros2 bag play`）。この repo は汎用の記録再生ではなく、指令・適用値・観測を別のログに分けること、全行に時計の種類と出どころを持たせること、受信側の期限と世代で古い指令を無害に拒否することに絞った小さな実験で、rosbag の代わりではない。
- **LeRobot**（https://github.com/huggingface/lerobot）は、遠隔操作（キーボードやゲームパッドなど）の記録をデータセットにする `lerobot-record` を持つ。この repo の目的は学習ではなく、記録と再生の差を段ごとに見ること。`prepare-dataset` は、試行ログから遷移データ（CSV → NPZ）を作って、別の repo の学習に渡すための出口で、この repo の中では学習しない。
- 試行ログを、そのまま [adaptive-motion-lab](https://github.com/hocky0301/adaptive-motion-lab) の入力にすることはできない。こちらの遷移 CSV は 10 列、あちらの必須は 16 列で、`step` と `step_index`、`command_u` と `commanded_u` のように名前も違う。対応表はまだ書いていない。
- 「送り続けないと止まる」期限（デッドマン）は、機械の安全でよく使われる考え方で、ここでは `valid_for_ms` として実装している。新しい手法として出すものではない。
